# Review Q&A（技术问答备稿）

回答按“先结论、再依据、最后限制”写。数字来自验证报告；合成数据与生产数据分开标注。

---

### 1. 为什么不直接做全局同步的 Draft？

因为代价与收益不匹配。Draft 是**未审材料**：客户日志、半成品结论、可能被丢弃的推断。把它实时同步
到中心，会引入服务器、鉴权、离线、隐私和可用性问题，而它要解决的只是“同一个人/同一 clone 的
两个人别互相覆盖”。V2 用 UUID 目录 + 独占创建 + DONE/hash + 严格 reader 解决本地写入与消费；
跨 clone 的冲突本来就应该在进入 Git 时解决，而不是在诊断时同步。

证据：验证报告 02 §3（10/10 轮覆盖、3/3 混合、崩溃半套）；03 §1（8 并发 8 目录、3 种崩溃均不被消费）。

限制：绕过 `inbox_put.py` 直接写文件仍会回到旧行为；文档与 groom 报告要写明覆盖范围。

---

### 2. 为什么 UUID 就够做 Draft 身份？Deployment ID 不要了吗？

Draft 身份只需要回答“这是哪一次沉淀的一组材料”，不需要可读、不需要绑定机器。UUIDv4 在并发、
独立 clone、复制仓库、目录改名下都不冲突；`(deployment, draft_id)` 会撞（两个 clone 都从 001 开始），
checkout 改名也会让 fallback 标签变化。

Deployment ID 仍然有用，但只用于 provenance/面板/诊断（“这条知识来自哪个部署”），不参与唯一性；缺失
写 `unknown`，不影响正确性。Case ID 是升格后才有的知识身份，Revision 用新 UUID + `supersedes`。

限制：UUID 目录不直观，所以报告/面板显示 `created_at + title + session`；UUID 碰撞概率按标准假设
可忽略，未单独测试。

---

### 3. 既然有 UUID、有查重，为什么还会出现重复 Case ID 或语义重复？

两类不同问题：

- **同 Case ID**：由 groom 确认，`build_index` 的 ID 唯一/文件名=ID/目录=category 三条硬检查会拦住
  同 ID 入库；V2 的 B 把同 ID 作为 mandatory，提前暴露。
- **不同 ID、语义重复**：机器只能提名，不能判定。V2 保证共享 upstream、同 ID、同路径、同 event、
  强判别式永远展示；同格/跨分类/有理由的跨 namespace 进 high；但**措辞完全不同、root cause 和 fix
  也改写**的重复仍可能漏。词法相似不是语义等价，所以不自动合并。

证据：V1 的 D2（改述）漏掉；V2 加 root/fix 字段信号后，合成集 9/9 必审对展示、D11 不展示
（`checkpoint-b-v2.json`）。这是机制验证，不是生产召回率。

---

### 4. 为什么 CI 不能自动判断“同一根因”？

“同一根因”要读日志、代码、版本、现场条件，还要判断“两个现象是不是同一故障的不同面”。这些不是
可枚举的机械判断。V1/V2 都只让机器做三件事：对齐字段、提名候选、标结构矛盾（同期望不同修法、
同 issue 不同根因、同 session 两处引用、版本与修复冲突）。结论由人写进 decision。

用 LLM 做 CI 判断的问题：不确定、不可复现、会随模型/提示漂移、无法解释“为什么这次判重复”；把它
做成门会让“通过”取决于提示词，而不是证据。LLM 可以在 groom 里做**辅助阅读**，但不能做 CI 门。

---

### 5. Checkpoint C 到底保证什么？不保证什么？

**保证（机械）：** 复核针对最新 `origin/main` 与本次 head/merge candidate；mandatory/high 的
decision 齐全且 `main_sha/head_sha` 未过期；同路径 add/add、同 Case 字段重叠、删除/重命名+引用、
生成物改动被标出；required check/批准/最新分支由平台强制。

**不保证：** 两个版本的语义是否自洽；reviewer 是否认真；候选是否召回完整；Git 干净合并是否等于
知识正确。

证据：C 原型能检出同路径、同 ID、字段重叠、重命名、过期（C1–C9）；但 C3/C8 仍然合入，因为没有平台
强制；同 Case 两个版本只能报“都改了”，不能判“矛盾”（03 §3）。

---

### 6. 为什么一定要 required checks / up-to-date（或 Merge Queue）？只用脚本 + 评审不行吗？

因为“脚本存在”和“合入被阻止”是两件事。当前 ruleset 只要求 PR，0 批准、无必需检查、无 up-to-date：
作者可以在检查红、分支旧的情况下合入。验证里 C8 就是这样：报告说 stale，merge 仍成功；PR body 写
旧 SHA 也能过 `verify_pr_body`（它只查标题）。

required check 解决“检查没跑/跑红也能合”；1 个非作者批准解决“作者自己批自己”；up-to-date 解决
“检查后 base 又前进”的时间窗（merge queue 是 P1 可选，不替代它）。没有这三样，C 只是建议。

**未验证：** GitHub 上这些行为的真实效果（只读 API，没有建 PR/改 ruleset）；必须在测试仓库先验证，
包括 `changes` skipped、批准失效、bot 推送。

---

### 7. 为什么 hash 不足以保证 provenance 可恢复？

hash 只证明“你手上这份字节等于记录的字节”，前提是**验证者能拿到这份字节**。Draft/trace 在本地、
gitignored，CI runner 拿不到；记录 `deployment_id + draft_id + hash` 不能让 CI 验证它存在。V2 分开
三件事：可追溯（记录来源，总能做）、完整性（只有可访问材料才校验）、可恢复（目标在 Git/耐久存储
才承诺）。档位写 `verified / declared / local-only`，`local-only` 明确“不验证”，不假装。

如果要求“合并的 Case 必须可恢复”，选“提交脱敏结构化材料”（P1 可选）；原始日志仍留私有存储，
因为隐私和体积。

---

### 8. 为什么不直接用 embeddings 或 LLM 做查重？

- embedding/LLM 相似度是**连续、不可解释、会漂移**的，不能回答“这两个字段哪里一样/哪里冲突”；
- 作为 CI 门不可复现：模型版本、提示、温度变化会让同一 PR 有时红有时绿；
- 作为提名也会把“措辞相似但根因不同”抬高，正好是验证里 D3 的陷阱；
- 现有检索是词法/结构（ADR-0002 明确不用向量 RAG），V2 复用 `sig/tok` 与字段比较，保持确定性。

可以用 LLM 在 groom 里帮 reviewer 读长文，但结论仍写 decision，且不进入 required check。

---

### 9. Reviewer 判错了怎么办？

机器门只能保证“有决定、决定新鲜、候选被看见”，不能保证决定正确。V2 的兜底：

1. **非作者批准** + dismiss stale/last-push approval，降低“作者自批”；
2. decision 文件写 `note` 与证据指针，评审可核对；
3. 高风险字段（`expected`/`fix_on_mismatch`/`compat`/`score_override`/新建 `common/`）继续双签；
4. 月度抽样与合并后审计（P2）：从 decision 与 provenance 抽样，发现漏判则回看候选规则；
5. 误诊归因走 trace（本地）与 case 修改，不靠“当时应该判对”。

这是“检测 + 复核”系统，不是“正确性证明”。

---

### 10. 如果 post-merge 生成物重建失败会怎样？

main 的索引/路由/timeline/entry-activity 会落后：新 Case 不进索引，诊断看不见；新路由词不生效。
当前 job 本身失败会红，但如果 job 没配置/密钥失效，main 没有任何 CI 在 push 后跑。

V2 加 `check_main_freshness.py`：每日（或每次 push 后）在 main 上跑 `rebuild_generated --check`，
dirty/失败就开 issue；同时保留现有 job。另修 E11（数字 SHA 崩生成器）和 E12（周快照过不了校验），
这两个是已经会让 job/快照失败的真实缺陷。

### 11. 最小实现范围是什么？

**P0（先做，能独立验证）：**
1. 平台：required `kb-required`（聚合，去 workflow `paths`）、1 非作者批准、up-to-date（merge queue 可选）、
   DEPLOY_KEY bypass；
2. 修 E11/E12 + main 心跳；
3. A：`inbox_put.py` + `draft_queue.py`（UUID/DONE/reader/legacy）+ skill/panel 接入；
4. C 最小版：`merge_recheck.py`（同路径/同 ID/字段 diff/过期）+ `verify_decisions.py` + decision 文件。

不做 B 完整版、provenance 检查、E10、观测，也仍然比现在安全得多。P1/P2 再加。

### 12. “PR 前 git pull、搜已有 PR、诊断前更新知识库”够不够？

**方向对，V2 采纳为 O1/O2，但不够。** 具体：

- `git pull` 是必要的开工纪律（仓库文档本来就要求 `git fetch`），但 pull 之后 main 还会前进；
  没有 up-to-date，旧分支仍可合。
- 搜开放 PR 很有价值：已验证 `refs/pull/*/head` 可见（378 个），单个 head 可 fetch；B 可以提前看到
  A 的 Case。但依赖网络/token；PR 会在检查后更新；没有 token 时无法区分 open/closed。
- 诊断前更新知识库改善候选质量，但诊断读本地检出，必须记录 `kb_rev`，且不能中途变。
- 它们都不解决草稿覆盖（草稿不在 Git），也不解决“合入时决定过期”。

所以：**O1/O2 降低“没看见”的概率，C 的 required check/up-to-date 才提供“不能绕过”的保证。** 两者都要，
不能互相替代。

---

### 13. 两个面板都要改吗？漏一个会怎样？

会“新草稿不可见”。仓库里有两个独立实现：`dsh-plugins/ascend-panel/panel-host.js` 与
`dsh-plugins/dsh-sleuth-panels/lib/index.js`。V2 要求同一个 reader 契约 + 同一组 fixture 的契约测试；
P2 再考虑合并实现。P0 估算已包含这部分，不是脚注。

---

### 14. 为什么不直接把生成物也放进 PR（旧纪律）？

旧纪律下同格并发会在 `_index.yaml`/分片撞行，需要人重跑；而且分片是嵌套 YAML，行级 union 会拼坏。
当前“PR 只交源文件、main job 重建”已经在生产运行成功（API 观测 6 次），应保留；V2 只加心跳与
失败可见性，不退回旧纪律。没有 job 的部署仍按文档二选一（PR 带生成物 + 本地 `--check`，或 main 上
`--sync`）。

---

### 15. 跨 namespace 到底查不查？会不会漏掉训练/推理同名问题？

**有理由才查。** 永远查 `common/`；训练↔推理在以下情况查：draft 的 workload_type 未知、framework 是
common、共享强关键词/upstream/event、root/fix 重合 ≥0.5、条件有交集。否则不查，报告写“未搜索”，
不写“无重复”。

原因：全库跨 namespace 词法扫描在 173 条库/11 drafts 上就产生大量无关对，reviewer 会疲劳；而
`common/` 本来就是权威记录，优先查它能覆盖大多数跨框架共性。

---

### 16. 真实规模下 B 会不会很慢/很多？

V2 原型在 173 条库 × 11 drafts 上 2–3 秒生成 300 对；展示 31 对。规模到 500 条/50 drafts 时：
生成是 O(drafts × library) 的字段比较，需要预筛（同 ns/同格/共享 token/共享 upstream）与缓存；
运行时预计仍是秒级，但**reviewer 时间**是主要成本（20–40 分钟/groom）。

如果溢出，V2 的规则是：mandatory 不藏；high 超 30 必须 ack；low 只报数。这样工作量有上限，代价是
“看过的比例”不是 100%，报告必须写清楚。

---

### 17. 旧 Case、旧 Draft 怎么办？要一次性迁移吗？

不一次性迁移。旧平铺 Draft 永久按 `legacy_flat` 读；旧 Case 不追溯 provenance（只对新增/合并强制）；
改 ID 用 `rename_case.py` + `redirects.yaml`；历史使用记录不重写，`verify_entry_activity` 认 redirects；
事故级指标按 `incident_key` 另算（P2）。迁移成本按条计，不承诺一次清完。

---

### 18. 如果管理员改动未获批准，还能做什么？

可以先做 P0 的代码部分（A、E11/E12、C 脚本、decision 检查），以 **report-only** 方式运行 1–2 周，
收集误报/工作量；但对外只能声明“检测与记录”，不能声明“阻止”。平台批准后再把 `kb-required` 设为
required、开批准/up-to-date。评审材料里要明确这条分界，避免“脚本上线 = 安全上线”的误读。
