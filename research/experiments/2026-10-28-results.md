# 并发提交与重复入库：7 个实验结果

这份记录对应《并发沉淀与重复入库：改进方案》（[../2026-10-27-kb-concurrent-merge-report.md](../2026-10-27-kb-concurrent-merge-report.md)）里列的 10 条风险。原文提到"原调查没有附完整运行日志或实验提交号"。这里补上其中 1、2、3、6、8、9、10 七条的可复跑实验、完整日志与读数。

4、5、7（同路径冲突、取一边丢补充、索引生成物冲突）在上一轮已经验证过，本次不重复。

实验日期是 2026-10-28。全部在临时克隆里跑，不碰本仓库。脚本是 `research/experiments/run_experiments.py`。完整输出在 `research/experiments/logs/`。关键读数在 `results.json`。

这些实验证明什么、不证明什么：每个实验人为构造一个状态，然后看现有检查抓不抓得住。它证明"这个状态一旦出现，会不会报"，不证明"这个状态在真实协作里多久出现一次"。两者的区别见文末"这些结论的前提"。

文中两个词先说明：

- 硬性检查：不通过就挡住合并。
- 提示：只报告，不挡合并。

## 结论一览

| 编号 | 问题 | 结论 | 有没有东西会报 |
|---|---|---|---|
| 1 | 同名草稿被覆盖 | 成立 | 没有（Git 也看不到，草稿不入版本库） |
| 2 | 两条重复 case 各自升格 | 成立 | 没有（所有检查都通过） |
| 3 | 跨分类重复漏掉 | 成立 | 没有。那条重复在症状上不可达 |
| 6 | 无冲突但合并内容不一致 | 成立 | 没有（检查只验结构） |
| 8 | 查重结论过期 | 成立 | 没有（这次连冲突都没有） |
| 9 | 改或删 id 后引用与统计错位 | 部分成立，分四档 | 使用记录：报错；先验引用：报错；回放夹具：只提示；重复结算：计数翻倍 |
| 10 | 同期号快照冲突 | 成立 | 合并时看得见。留一份后校验仍通过，少一期没人报 |

一句话：脚本检查能覆盖的问题，多数有硬性检查（第 9 条有两项会报错）。内容判断与"两台机器各算一遍"的问题，都没有硬性检查。

---

## E1 同名草稿被覆盖

一个克隆开两个工作区，模拟同一台机器上的两个会话。两个工作区各自解析 inbox 路径，先后写同名草稿。

结果：

- 两个工作区解析到同一个目录：`<主检出>/postmortems/inbox`。
- A 先写，B 后写同一文件名。B 的内容留下，A 的内容消失。
- 两次写入都没有报错。两个工作区的 `git status` 都是空的。草稿被 `.gitignore` 挡着，覆盖没有痕迹。
- 对照：id 不同时，两个文件都在。

结论：成立。同名覆盖没有提示，只能靠写前检查。

---

## E2 两条重复 case 各自升格

两个分支各写一条 case。症状与判别条件相同，id 不同（`TEST-DUP-A` 与 `TEST-DUP-B`）。各自重建索引，然后依次合并。

结果：

- 合并第二条时撞 3 个生成物文件：总表、类视图、ns 兜底视图（category 未定时读的那份）。按标准动作重跑索引后，两条都在。
- 五道检查全部退出码 0：`build_index --check`、`verify_case_draft --all`、`verify_references --check`、`verify_entry_activity`、`verify_metrics --check`。
- 两条的症状数组相同，`quickly_check.primary.expected` 相同。同格读侧视图里，两条各占一行。

结论：成立。两条重复可以一起进库，没有检查报重复。

---

## E3 跨分类重复漏掉

同样两条，症状相同。一条放进 `training/verl/interrupt`，一条放进 `training/verl/performance`。

结果：

- 合并没有冲突（不同格子）。
- 五道检查全部通过。
- 两条分别只出现在各自的读侧视图里。interrupt 视图有 A，performance 视图有 B，交集为空。
- 路由检查对 B 的结论：期望性质是 performance，实际首个命中是 interrupt（`interrupt←\btimeout\b`）。检查给出告警："首个命中不是期望的性质"。

结论：成立。这条比第 2 条多一层问题：B 在"all_to_all timeout"这条症状上不会被路由到，写了但用不上。任何"同格子内比对"的办法按定义看不见它。

---

## E6 无冲突但合并内容不一致

同一条 case 上，A 把 `compat.ranges` 从 `0.21.0` 扩到 `0.21.0, 0.24.0`，声明 0.24.0 也受影响。B 把修复动作改成"升级到 0.24.0"。两处相隔较远。

结果：

- 合并只撞索引 3 个文件。case 文件本身不在冲突里，Git 干净合并。
- 合并后的 case 同时写着：受影响版本包含 0.24.0，修复动作是升级到 0.24.0。
- 五道检查全部通过。

结论：成立。同一个版本既被判为"有问题的版本"，又被判为"修复目标"。脚本不判这种内容矛盾，人也不一定会看。

---

## E8 查重结论过期

B 在旧主干上把案例判为"新根因"，文件头写 `pre-triage: new_pattern`。提交并跑检查。随后 A 把同现象的案例合入主干。B 合并最新主干后再跑检查。

结果：

- B 在合入前跑检查：全部通过。
- B 合并最新主干：没有冲突。Git 把 A 的索引条目叠了上去。
- 合并后，B 的文件仍标着 `new_pattern`。实验里的流程没有一步重新判断它和 A 的关系。
- A、B 两条都在库里。五道检查全部通过。

结论：成立，但要说准。没有的是自动重新判断，不是"流程里没人负责查重"。仓库的 PR 预核清单要求查与相邻 case 是否同根因。groom 也有相似对提示。这两处由人或 agent 执行，可以留空，没有脚本检查。我原本预期 rebase 会撞索引、逼人看一眼。实测这次没有冲突，所以连"被提醒"的机会也没有。

---

## E9 改或删 id 后的引用与统计错位

分四个子实验，四种后果的约束力不同。

9a 使用记录。先补一条指向 `VLLM-ASC-15087` 的真实使用记录（`kind: case`），此时校验退出码 0。再删掉这条 case，校验退出码 1，报"案例 id 在知识库里查不到"。

这是硬性检查。删 id 前要先把使用记录处理掉。

9b 先验引用。删掉被 `references/errors/cann-runtime.yaml` 引用的 `VLLM-ASC-12989`。`verify_references --check` 退出码 1，报三处 `sources[].cases` 或 `source_cases` 指向不存在的 case。

这也是硬性检查。

9c 回放夹具。删掉 `MSLLM-1655`，重建索引，再跑 `eval_scorecard --check`。退出码 0，只打一条"目标 case 不在索引中"的提示。

这是提示，不挡合并。夹具指向旧 id 时不会报错。

9d 重复结算。给同一个 case 追加两条 `resolved: 1` 的行，时间戳不同。`verify_entry_activity` 退出码 0。行的键是 `(run, kind, id)`，时间戳不同就不算重复。重建生成物后，该 case 的 `resolved` 从 1 变成 3。

同 case 的多行不会被判重。边界要说清：实验只证明了这一点。它没有证明"同一次现场验证被算两次"。行里没有 session 字段，两次结算与两次真实验证在数据上长得一样。要产生重复，需要同一份 trace 在两台机器各结算一次（交接包、手工复制）。`import_trace.py` 只防同一份包重复落位，不防后续各自结算。这一条是结构性缺口，没有构造出完整复现。

结论：部分成立。改 id 不是随便删。使用记录和先验引用会拦住（硬性检查）。回放夹具只提示。重复结算的缺口存在，但比原表述窄。

## E10 同期号快照冲突

两个克隆在同一天各生成一期指标快照。期号按"ISO 周 + 日期"生成，两台机器算出的都是 `2026-W44-live-1028`。为了体现本机读数不同，把 B 那期的 `case_total` 改成 999。

结果：

- 合并时同名文件冲突，冲突文件一个：`metrics/timeline.d/2026-W44-live-1028.yaml`。
- 为省事留 A 那份：重建后 9 期，`case_total` 是 168。另一台的 999 消失。`verify_metrics --check` 退出码 0。
- 正确解法：两边都留，第二份文件名和 `period` 字段一起改成 `-2`。重建后 10 期，两期读数分别是 168 和 999，校验退出码 0。

结论：成立，但只在特定条件下：同一部署的两台机器、同一天、都跑了周界整理。期号带日期，换一天就不撞（会变成同一周两期读数，另一种问题）。跨部署本来就不该合并 `metrics/timeline.d/`。另外，实验里"读数不同"是我改了一个字段来模拟。真实差异来自两台机器各自的 `traces/`。这一点是模拟，不是实测。

## 这些结论的前提

10 条不是独立发生的，也不是每条都会自然出现。要出现，分别需要：

| 编号 | 出现的前提 | 实验是否构造了 |
|---|---|---|
| 1 | 同一克隆（多个工作区）+ 两人选了同一个 case id | 是 |
| 2 | 无额外条件：两人独立沉淀同一问题、id 不同 | 是 |
| 3 | 同一根因被判到不同分类或不同命名空间（判断不一致） | 是（构造得偏强，见下） |
| 4 | 两人用同一个 id（按 issue 号命名时常见） | 是（上一轮） |
| 5 | 人在解冲突时整份取一边 | 是（上一轮） |
| 6 | 两人都判 variant，且改同一条 case 的不同字段 | 是 |
| 7 | 两边都重建索引，且改动落在同一段文本附近。不保证冲突 | 是（上一轮三人实验。E8 两人同格就没有冲突） |
| 8 | 同 2，强调时间：先判新增，对方后合入 | 是 |
| 9 | 改或删一个已被引用的 id。四种引用后果不同 | 是 |
| 10 | 同一部署、同一天、两次周界整理 | 是（读数差异是模拟） |

几组其实是同一条机制的不同侧面，不是 10 个独立问题：

- 2 和 8 是同一件事（重复入库）。8 是它在时间上的解释。
- 3 是 2 的跨分类版本。
- 4 是 5 的前置条件。
- 1 和 2 分居草稿阶段与入库阶段。
- 9 和 10 都是"同一件事被两个副本各记一次"。

## 需要修正的几处说法

- 第 7 条"每次同格并发都撞 3 个生成物文件"。那是三人实验的读数。两人同格不一定撞：E8 里两人同格合并，没有冲突。冲突取决于两边改动是否落在同一段文本附近。
- 第 8 条"没有任何步骤重新判断"。仓库的 PR 预核清单要求查与相邻 case 是否同根因。groom 也有相似对提示。缺的是强制与脚本执行，不等于没有流程。
- 第 9 条"统计错位"。使用记录与先验引用都是硬性检查，删 id 会被拦。只有回放夹具是提示。"重复结算"这一档没有构造出"同一次验证被算两次"的完整复现。只能说行里没有 session 字段，两种情形在数据上不可区分。
- 第 3 条的实验构造。我用"相同的症状 + 不同分类"。这在正常判断下自相矛盾（同症状应同性质）。更准确的场景是误分类，或同一根因落在两个框架命名空间（verl 与 mindspeed 都涉及）。
- 第 10 条。只在同部署、同日、两次周界整理时发生。期号带日期，跨天不撞。

## 实验过程里发现的一处检查缺陷

`verify_case_draft.py` 在过滤生成物时，会跳过"路径里任一上级目录以 `_` 开头"的文件。这个判据原本是为了跳过 `references/_archive/` 与 `references/_procedure-index/`。它用的是绝对路径的所有片段。只要检出路径里有一级目录以 `_` 开头，`references/` 下的词条会被全部跳过。

实测：把克隆放在 `research/experiments/_work/...` 下，`load_reference_index()` 返回 0 条。`verify_case_draft --all` 报 14 条"ref_knowledge 悬挂引用"的假告警。换到不带下划线的目录后，同一份内容返回 267 条，检查通过。

影响：检出目录名带下划线前缀（例如 `_repo`）时会误报。CI 的检出路径通常不带下划线，所以线上没有暴露。这不是本次 10 个问题之一，单独记一条。

## 局限

- 合成 case 是最小结构，只用于验证"检查会不会报"，不代表真实 case 的复杂度。
- "两台机器"用两个分支或克隆模拟，没有真的跨机。对 Git 合并行为没有影响。对 `traces/`、`inbox` 这类本地共享路径，只验证了同一克隆多工作区的情形。
- 期号按实验当天生成。换一天期号不同，结论不变。
- 实验在 Windows 上跑，脚本里统一设了 `PYTHONUTF8=1`。Linux 上结果应当一致。
