# 并发入库实验：方法记录

这份文档说明 `research/experiments/` 下 7 个实验怎么做的，供复跑或审查使用。结果与结论在 [2026-10-28-results.md](2026-10-28-results.md)。

## 目的与边界

目的只有一个：验证某个并发状态出现时，仓库现有的检查会不会报。

不测三件事：

- 这个状态在真实协作里出现的频率；
- 真实工程师的草稿长什么样；
- 跨机器的网络与磁盘行为。

所以实验是构造状态，不是观察生产流量。

## 环境

实验时的本机环境：

| 项 | 值 |
|---|---|
| 系统 | Windows |
| Git | 2.45.1.windows.1 |
| Python | 3.12.2 |
| PyYAML | 6.0.3 |
| 编码 | 所有子进程设 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8` |

仓库基线是实验时的本机 HEAD。实验只读本仓库的已跟踪文件。

## 沙箱怎么建

每个实验一个独立克隆，实验之间不共享状态。步骤：

1. `git clone -q --no-hardlinks <本仓库> <工作目录>/<实验>/repo`。
2. 在克隆里设置 `user.name` 与 `user.email`，否则提交失败。
3. 从克隆的 `main` 建分支，构造状态。

克隆只带已跟踪文件。`traces/`、`postmortems/inbox/` 里的草稿、exec-log 这些运行时件不在克隆里。这与 CI 的干净检出形态一致。

实验结束后默认删除工作目录，只保留日志与读数。

## 构造 case

合成 case 用固定模板，字段取能让 `verify_case_draft.py --all` 通过的最小集合：

- `id`、`title`、`category`
- `compat`（框架与版本区间）
- `symptoms`
- `diagnosis`（至少一步，含 `check` 与 `expected`）
- `quickly_check.primary`（`command_template` 与 `expected`）
- `root_cause`、`fix`、`severity`、`fix_type`

模板在 `run_experiments.py` 的 `CASE_TMPL`。每个实验只改需要的字段。这样做的原因：合成 case 只用来触发检查行为，不代表真实 case 的复杂度。

## 七个实验各自构造什么

| 实验 | 要复现的状态 | 构造步骤 | 观察点 |
|---|---|---|---|
| E1 | 同一克隆的两个工作区写同名草稿 | 一个克隆加两个 `git worktree`，各自解析 inbox 路径，先后写同一个文件名 | 两个路径是否相同；后写是否覆盖；`git status` 是否有提示 |
| E2 | 两条重复 case 用不同 id 进库 | 两个分支各写一条同症状、同期望值的 case，各自重建索引，依次合并 | 冲突文件；解冲突后两条是否都在；五道检查的退出码 |
| E3 | 同一根因分到不同分类 | 两个分支，一条放 `interrupt`，一条放 `performance`，其余同 E2 | 合并是否冲突；两条各进哪个视图；路由检查判定哪条可达 |
| E6 | 两人改同一条 case 的不同字段 | 先建基础 case；分支 A 扩 `compat.ranges`；分支 B 改 `fix_on_mismatch`；合并 | case 文件是否冲突；合并后两个字段是否矛盾；检查是否通过 |
| E8 | 查重结论在对方合入后过期 | 分支 B 先写 `new_pattern` 草稿；主干先合入同现象的 A；B 再合并最新主干 | 合并是否冲突；B 是否仍标 `new_pattern`；两条是否都在 |
| E9 | 改或删 id 之后的四种引用 | 四个子克隆：补使用记录后删 case；删被引用的 case；删夹具目标并重建索引；追加两行同 case 的记录 | 每个检查的退出码；`resolved` 计数 |
| E10 | 两台机器生成同一期号快照 | 两个克隆同一天各生成一期；B 的 `case_total` 改成 999；合并；分“留一份”与“两边都留”两种解法 | 冲突文件；留一份后另一份读数是否还在；两期是否都能通过校验 |

## 合并与解冲突的固定动作

合并统一用 `git merge --no-ff`。冲突分两类处理：

- 生成物冲突（`knowledge/_index.yaml`、`knowledge/_index/`）：取一侧，重跑 `python scripts/build_index.py`。不手改。
- case 文件冲突：保留双方版本，留给人工判断。实验里不代替人决定内容。

E6 与 E8 故意让 case 文件不冲突，用来观察“没有冲突时会发生什么”。

## 检查清单

每个实验合并完成后跑同一组检查：

| 命令 | 看什么 |
|---|---|
| `python scripts/build_index.py --check` | 索引是否覆盖全部 case，行与内容是否对得上 |
| `python scripts/verify_case_draft.py --all` | 字段、枚举、引用、正则是否合法 |
| `python scripts/verify_references.py --check` | 先验词条的引用是否悬挂 |
| `python scripts/verify_entry_activity.py` | 使用记录的行与 id 是否有效 |
| `python scripts/verify_metrics.py --check` | 指标时序的结构与期号是否合法 |

退出码 0 表示通过。非 0 表示有报错。提示不改变退出码：`eval_scorecard --check` 打出“目标 case 不在索引中”的提示时，退出码仍是 0。

## 记录方式

脚本里每个实验用一个记录器，记三类内容：

- 每条命令与它的完整输出；
- 关键读数，写成“名称 + 值”；
- 结论需要的原始文本，例如合并输出、检查报错。

输出落到两个地方：

- `research/experiments/logs/E*.log`：逐命令的完整日志；
- `research/experiments/results.json`：每个实验的关键读数，机器可读。

脚本不做自动断言。判定由人读日志得出。这样做的原因：实验要回答的是“会不会报”，不是“断言是否为真”；把结论写死在断言里，容易把没观察到的情况当成通过。

## 复跑

```bash
# 全部
python research/experiments/run_experiments.py

# 单个实验
python research/experiments/run_experiments.py --only 2

# 保留临时克隆，便于手工检查
python research/experiments/run_experiments.py --keep
```

脚本会覆盖 `results.json` 与 `logs/E*.log`。临时克隆在 `research/experiments/work/`，默认跑完删除。

## 可复现性注意

- 期号依赖运行日期。E10 的期号是 `2026-W44-live-1028`，换一天跑会得到新期号，结论不变。
- 临时克隆的路径不要含 `_` 开头的目录。原因：`verify_case_draft.py` 会跳过“绝对路径里任一上级目录以 `_` 开头”的文件，`references/` 会被全部跳过，引用索引变成 0 条。实验脚本把工作目录命名为 `work`，就是为了避开这一点。
- Windows 上 Git 对象是只读的。删除临时克隆前要先去掉只读属性，脚本里有处理。
- 实验只记录结果，不测耗时。E10 的两台机器读数差异是改字段模拟的，不是真实采集。

## 不测什么

- 不测这些状态出现的概率；
- 不测真实草稿的内容质量；
- 不测跨机同步、网络、磁盘故障；
- 不测面板与 UI 在这些状态下的显示。
