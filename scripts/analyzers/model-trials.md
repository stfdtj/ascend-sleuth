# 在工作机上验证另外六个分析器

状态：提议

本页记录 7 个分析器版本中的六项实验。复跑本页时，C 组固定检出 `1baa5f843c4adedfb67eb9d3765ef88b0aaa4058`。当前分支的环境工具只做快照比对，单卡性能对比采用[独立于输入格式的判读方法](../../references/methodologies/performance-baseline-comparison-reading.yaml)。

用已定位的真实案例，比较原版诊断、补充读法、再启用分析器后的证据和判断。每个分析器准备一题材料充分的案例和一题材料不足或不可比的案例。本页供实验组织者和评审使用。iBMC 单独按[分支首页](../../README.md#在工作机上跑-ibmc-诊断对照)运行。

## 做完得到什么

每个分析器形成两题的三组报告及一张评分表。逐题判断分析器有没有找到额外的可核证据、有没有减少误判或补证轮次。6 个分析器共 12 题，每题 3 次独立诊断，共 36 次。可以按找到的材料逐个完成。

## 准备材料

复用 iBMC 实验的工作机、模型、Python 和权限。每题准备原始材料、简短题干、单独存放的评审答案。题干只给当时的现象、已知环境和材料位置。评审答案提前写明已确认结论、证据文件和原值、首轮不能确定的事项，以及要补的最少材料。

用未参与开发或回归测试的历史现场案例。优先找原本就缺材料的案例。需要模拟缺项时，只改实验副本，注明移除了什么，再给三组复制同一份输入。给案例和文件夹用中性编号，包内文件名保留原样。

| 分析器 | 材料充分题 | 材料不足或不可比题 |
|---|---|---|
| `issue-analyzer` | 要一份已定位的中断日志。带失败 rank 的 `plog`、框架栈及对应时间段的设备或宿主机日志。优先找有重复报错、也有明确首个有效故障的案例。 | 找一份缺失败 rank 日志或缺时间对应关系的多机日志。保留重复报错，让三组判断能定位到哪一层、该补哪个 rank 和时间段。 |
| `ascend-dump-analyzer` | 要正常端和异常端的两份原始环境 dump JSON，记录同一负载和已知变更。优先找有已复核的版本或配置漂移，且回退或复测结果可查的案例。 | 要一份缺关键组件版本的原始 JSON。评审记录缺什么版本、哪些配套关系因此无法判断。 |
| `prof-compare` | 要同一负载、同一采集范围的单卡基准和异常对比。优先找已有 `msprof-analyze compare` 生成的 `.xlsx`，同时保留 A/B 对应关系、采集窗口、吞吐或时延及已复核的差异。 | 要缺关键页的 compare 工作簿，或找两次采集窗口或负载不一致的现成工作簿。保留 A/B 元信息，使差异的归因边界可核对。 |
| `cluster-analysis` | 要一次多卡 Prof 采集根目录，或该次已有的 `cluster_analysis_output/`。带预期 rank 数、Step 范围和实际吞吐。优先找已确认慢 rank 的案例。 | 要同一类采集中缺部分 rank 或缺目标 Step 的包，同时给出预期 rank 和采集窗口。用来检验是否会把局部数据当整集群。 |
| `cluster-compare` | 要变更前后两份含 `cluster_analysis_output/` 的集群结果，按 A 基准、B 对比。带 rank 映射、负载、共同 Step、有效吞吐及已核对的受影响阶段。 | 要两份都能读取的集群结果，但没有可对齐的 Step，或一侧缺相应 rank 映射。保留能说明不可比的元信息。 |
| `cpu-host-performance` | 要已有 ftrace 或 Host 采集包，含目标进程及线程对应关系。优先找有同一时间窗的 NPU 侧 trace 或独立对照结果，能复核 Host 调度现象的案例。 | 要只有 Host 侧 trace、缺 NPU 同期证据或线程身份不齐的案例。保留能确认的 Host 读数，考察是否会把它直接写成 NPU 慢的原因。 |

`prof-compare` 需要预装 `openpyxl`。从两份原始单卡 Prof 目录生成 `.xlsx` 时，还需要 `msprof-analyze`。多卡 Prof 的 `cluster-analysis` 会在输入目录写 `cluster_analysis_output/`，为 C 组提供独立工作副本。`cluster-compare` 的文本输入保留 `cluster_step_trace_time.csv`。有 `communication_group.json` 时也保留，缺失时记录通信分组的证据边界。已有支持的集群 DB 也可用。

## 步骤

1. **固定三组的版本和材料。** 按[分支首页](../../README.md#在工作机上跑-ibmc-诊断对照)准备独立克隆和子代理，按下表检出指定提交。每题三组用同一模型、推理设置、题干、原始材料和通用脚本权限。三组都从头诊断，跳过已有案例、历史复盘、历史诊断记录和其他组结果。

   | 组 | 检出版本 | 此轮额外能力 |
   |---|---|---|
   | A | `75f6e39` | 原版 `diagnose`。可按需读三组共同的已有参考词条。 |
   | B | `75f6e39` | 原版 `diagnose`，另提前提供下面对应分析器的一条读法。 |
   | C | `1baa5f843c4adedfb67eb9d3765ef88b0aaa4058` | 与 B 相同的读法，另启用当时的内置分析器。 |

   只把对应行交给 B、C，整份实验说明及评审答案由组织者保管。这里测的是**事先提供读法**的效果。自动检索能否找到词条需另测。

   | 分析器 | 交给 B、C 的读法 |
   |---|---|
   | `issue-analyzer` | 按主机、rank、日志类型和时间窗建立对应关系。回到原文核对首条能解释故障的事件及上下文。确认由同一事件引起的重复报错归并记录。 |
   | `ascend-dump-analyzer` | 先核对硬件与软件版本，再按字段比较环境变量和启动配置。缺字段记未知。配置差异先作为线索，用复测或变更记录核对因果。 |
   | `prof-compare` | 记录 A/B、负载、采集窗和单位。先看整体时延或吞吐，再回到差异所在工作表、算子或通信项核对绝对耗时。 |
   | `cluster-analysis` | 先记录实际覆盖的 rank、Step 和预期范围。对慢 rank 用同一 Step 的计算、通信、等待或时间线证据缩小原因。 |
   | `cluster-compare` | 先核对同负载、rank 映射、采集窗和共同 Step。分别看阶段耗时、计算、通信和等待。缺对照条件的项目标为不可比。 |
   | `cpu-host-performance` | 先核对 PID、线程、采集窗口和可见事件。把 Host 调度或资源现象与同时间窗的 NPU 活动对照。因果证据不足时写待验证。 |

2. **先验收工具，再派发模型诊断。** 组织者按[调用说明](README.md#直接调用)启用分析器，执行 `python scripts/analyzers/cli.py status --json` 和 `python -m unittest tests.test_analyzers`，核对开关与依赖。用开发样例或另外一份输入手动跑一次本轮要测的输入形态，检查产物和输出位置。

   在诊断会话里，A、B 保持 `SLEUTH_ANALYZERS=off`。C 的 `status`、`list` 和 `run` 都设为 `on`。命令各用一个新 shell 时，每次在同一 shell 设置。C 按 `diagnose` 自己选工具，记录未调用、选错、部分成功或失败，并保留该组报告。开发验收阶段可以指定工具运行。

3. **逐题收齐三份结果。** 将下面的指令和本轮材料位置交给主代理。评审前隐藏组名，记录报告、工具状态、总耗时和补证轮数。有实际用量读数时再记录模型用量。

   ```text
   按 scripts/analyzers/model-trials.md 组织指定分析器的两题对照。每题给 A、B、C 各开一个新子代理，分别在独立克隆运行。每个子代理只收到同一个题干、该题材料路径、对应组的能力与输出路径。B、C 额外收到对应的一条读法。组织者保管评分表和评审答案。子代理按 diagnose 独立给出判断、原始证据位置、下一步和待补材料。收齐报告后再汇总。
   ```

## 怎么确认做对了

按 iBMC 的五项评分，每项 0–2 分，满分 10 分。逐份看结论、证据、观察项、缺证据、补证。两名评审独立打分。提前写下每题的通过条件和会导致误判的说法；工具退出成功与诊断正确分开记。

| 分析器 | 材料充分题看什么 | 边界题看什么 |
|---|---|---|
| `issue-analyzer` | 能指出影响链上的首个有效事件，引用原始文件、时间和 rank。将重复报错归到同一事件时，说明依据。 | 明确可确认的范围。缺失败 rank 或时钟对应时，保留跨机先后判断，并指出要补的日志。 |
| `ascend-dump-analyzer` | 对关键字段给出两端原值、差异方向，区分已观测漂移和由复测支持的原因。 | 缺版本时配套结论为未知，指出缺失的组件和版本信息。 |
| `prof-compare` | A/B 方向、单位和绝对差值正确，能指出哪个算子、通信项或模块支撑结论。 | 指出缺页或负载、采集段差异对比对的影响，提出最少补料。 |
| `cluster-analysis` | 给出实际 rank、Step 覆盖，定位慢 rank 或阶段并引用同窗口证据。 | 结论只覆盖已观测范围，并列出没覆盖的 rank 或 Step。 |
| `cluster-compare` | 先通过可比性检查，再给出阶段耗时差和贡献方向，回查共同 Step 与对应数据。 | 共同 Step 或映射不足时指出不可比。即使生成报告，也保留归因判断。 |
| `cpu-host-performance` | 能把调度、争抢或频率现象定位到线程和时间段。NPU 侧影响有独立证据时才给出因果判断。 | 保留可核的 Host 现象，明确 NPU 因果待证，并给出下一份所需材料。绑核建议只作为报告内容。 |

结果表至少记录：案例编号、提交和模型、三组评分、最关键的原始证据位置、C 的调用及状态、总耗时、补证轮数、评审分歧。一项工具有帮助也应写明发生在哪题。两题结果用于本轮选型，样本积累后再估计整体效果。

## 出错了怎么办

- 预检缺 `openpyxl` 或 `msprof-analyze` 时，记下环境结果。先用通过预检的输入形态做模型对照，缺依赖路径单独记录。
- 调用超时、无产物或返回 `partial` 时，按当前能取得的证据完成诊断。记录原因、覆盖范围及缺项。
- 发现题干暴露答案，或某组读到了历史案例和其他组结果时，保留失败记录，从干净目录重跑相应组合。
- 缺独立真实案例时先标「开发验收」。仓库里的回归样本可用于验收命令和产物。

## 怎么结束和清理

把报告、工具结果和评分表留在工作机的获准目录。确认每次运行的版本和证据位置可回查后，再移除实验克隆和输入副本。原始材料及评审答案按各自的留存流程管理。
