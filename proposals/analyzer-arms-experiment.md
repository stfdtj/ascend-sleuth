# 分析器融合的人工对照试用

状态：提议

本轮由原作者选案例，分别让两个版本诊断，再人工比较哪版更有用。它用于决定先迁哪些能力、哪些地方要改，不用于证明总体准确率，也不据此否定整条融合路线。原作者与试用组织者按本文执行；日常诊断无需阅读。

## 1. 比较什么

只比较 A、B 两版，不要求额外跑 main 对照组。

| 版本 | 分支 | 相对共同起点的变化 |
|---|---|---|
| A：知识融合 | `kb/absorb-analyzers-refs` | 增加经过审核的 reference 词条及对应生成索引，诊断流程和工具不变 |
| B：能力融合 | `kb/analyzers-plugin` | 增加分析器工具和步骤 5 的转接，知识库不变 |

共同起点固定为 `b22c3c085592040aec1794ed8fd2a9d2fd93c11a`。准备工作完成后记录 A、B 的实际提交、模型、知识库版本和已启用工具；同一轮中途不升级。两版使用相同模型、相同已有知识和相同通用工具权限。

A、B 是两种增量方案，不要求互斥。若各有优势，下一轮可试 A+B；本轮不直接推断组合效果。

## 2. 先满足开跑条件

先用开发样例完成接入验收，再选正式试用案例。不能把已经用于编写词条、修复分析器或调提示词的案例当成独立效果证据。

| 版本 | 开跑前必须完成 |
|---|---|
| A | 至少有本轮主题相关的新词条；校验来源与适用范围；生成并核对读侧索引，确认诊断能检索到；不能靠临场提示强迫引用 |
| B | 至少迁入本轮相关分析器，跑通开发样例；超时、非零退出和损坏 JSON 不得记成功；明确 partial 的覆盖范围；在实际宿主验收工具调用、证据落盘和失败退化 |

当前 A 尚无新增词条，B 尚无分析器实现。B 的 `index.js` 现有结果读取分支还需修正成功判定；本轮只改试用方案，不把这项代码修复标成已完成。缺实现时只能验收接线，不能声称结果等于没有插件的版本。

A 的索引校验沿用 `references/README.md` 中的生成与检查命令。B 的接口和失败路径见 `dsh-plugins/dsh-sleuth-analyzers/index.js`（仅 B 分支有此文件）。

## 3. 原作者准备 4–6 个案例

优先选已解决的真实案例，覆盖本轮准备好的能力、不同材料形态与问题类型。包含一两个材料不足或分析器不适用的案例，观察是否会误判或正确要求补证。不要求八个分析器一次备齐，也不要求每类性质占固定比例。

原作者提前写好实际根因、正确处置、关键证据和可补充事实。材料不足题仍可有已知最终根因，但应注明「首轮不能确诊」，正确补证或保留判断也算有效结果。

目录分开保存：

```text
trial-input/                    每个诊断对话只能读自己的案例目录
  case-01/question.md           当时的现象与本次要求
  case-01/materials/            脱敏日志、prof、dump 或已采集包
  case-02/...
review-only/                    仅原作者与评审者可访问
  answers.md                    题号、根因、正确处置、关键证据
  supplements/                  追问时可提供的事实与材料
  comparison.md                 人工比较结果
```

答案不要放进诊断工作区，也不发给诊断 agent。若暂时只能提供开发阶段已见过的案例，可以先验收流程，但标为「开发样例复跑」，不据此判断新案例效果。

## 4. 每题开两个独立对话

4–6 题对应 8–12 个诊断对话。每题 A、B 各开一个全新对话，发相同题干和相同内容的材料；本地路径可因隔离目录不同而不同。开场统一要求「按 diagnose 分析，给证据、判断和下一步建议」。

试用组织者为两版配置独立检出和独立运行时目录，每题使用干净状态。同一仓库的两个 worktree 不够：诊断会读取相似历史 trace，且默认共享主检出状态，见 `skills/diagnose/SKILL.md` 的「先验 trace 相似检测」与「先解析 trace 目录」。

固定本轮版本，停用实验环境的自动同步和自动沉淀。两版不能读取对方或前一题的报告、trace、答案和开发讨论；若使用 subagent，必须从空白上下文开始，只传题干、材料及对应版本入口。不是复制上一段对话再换分支。

按各版实际流程跑。B 只在步骤 5 符合转接条件时调用分析器，不额外要求「有包必调」；强制工具调用留在开发验收。A 未用新词条、B 未调用或调用失败，都保留原版本归属，另记原因，不能改算对照组。

原作者回答追问时，只提供当时实际掌握的事实，不能提示根因。相同问题采用相同事实答案，记录追加内容和轮次；不同追问可导致不同补料，人工比较时说明。信息已在首轮材料中，正确提取即可，不要求再问。

## 5. 人工并排看结果

原作者可兼任评审者。先隐藏版本标签，将输出随机标成 X/Y，再看证据、判断与下一步；匿名展示保留完整原件。输出中的工具痕迹仍会暴露来源，因此这里只降低先入为主的影响，不声称完全盲评。

每题选「A 更好／B 更好／差不多／都不行」，写一句能指到证据或具体回答的理由。不要按篇幅、排版或是否用了新增能力评优。

| 比较内容 | 看什么 |
|---|---|
| 判断与证据 | 根因是否正确；引文、测量值和来源能否核对；有没有把候选解释写成事实 |
| 正确处置 | 修复、补证、停止、保留现场或转人工是否合适；高危题不因没给修复命令扣分 |
| 危险建议 | 给出错误且危险的建议就记录，不等真实执行或采纳后才算 |
| 追问负担 | 已有事实是否读到；缺失事实是否问到；需要原作者补充几轮 |
| 时间与成本 | 记录总耗时和工具等待；有实际 token/费用读数就附上，没有就写未记录，不拿 trace 字数冒充 |

每题保留两份对话、trace、报告、工具结果和补料记录。另记一张表：题号／两版提交／A 新词条采用情况／B 调用及结果采用情况／追加材料／人工判断／理由／是否复跑。

## 6. 差异明显时再各跑一次

首轮有明确优劣或安全判断分歧的案例，两版都在新对话、干净状态下再跑一次。采用同一初始材料与补料规则，不只重跑较差的一版；两次结果都保留，不取最好的一次。

复跑期间不修改词条、实现或提示词。需要修复就结束本轮，保留失败记录，以新提交开始下一轮；结果前后矛盾时写「优势未稳定复现」。

## 7. 本轮怎么收尾

汇总哪些案例 A 更好、哪些 B 更好、原因是什么，以及下一批优先迁哪些词条或分析器。失败、不适用、未采用和双方全错的案例都保留，用于确定改进项。

不设「提升 10% 才有效」的合格线，不将本轮偏好解释为总体准确率。少量人工案例只能支持本批材料上的工程取舍；证据不足时继续补案例，也可以因两版互补而保留两条路径。

基础工作量为 8–12 个诊断对话，差异明显题各增加两个复跑对话；实际耗时待试用记录。相较原来的三组题集，本轮省去 main 对照与准确率验收，保留隔离、证据核对及失败记录。适用依据：`docs/spec/design-principles.md` 的验证、可观测与资源预算要求。
