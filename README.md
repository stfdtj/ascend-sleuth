# 实验分支 A：把 8 个分析器的经验写成知识库条目

这条分支是实验分支，首页临时换成这份说明。项目原本的说明在 [main 分支](https://github.com/pillumina/ascend-sleuth)。

一句话：不改诊断流程、不加工具，只把 8 个分析器里「下次遇到同类问题还用得上」的判断依据，写成 sleuth 诊断时能查到的条目。

## 你（原作者）只要做一件事

把三样东西放进一个目录，然后把目录路径贴给 agent：

```
analyzers-input/
├── samples/        每个分析器一个子目录，放 2–3 份脱敏后的输入
│                   （prof 目录、dump_info、日志包都行，目录名用分析器名字）
├── answers.md      每份样例的正确答案：根因是什么、正确处置是什么
└── sources.md      每个数字和做法的出处：文档名 + 页码，或公开链接；
                   只有你手记没有出处的，直接写「手记」
```

然后只要说一句：

```
材料在 D:\analyzers-input
```

剩下的 agent 读完这份文件自己去做。

**为什么只要这三样**：没有样例，写出来的条目对错没法验；没有答案，判定没有依据；没有出处，条目只能当个人经验，不能当官方事实用。

## agent 读到这里要做什么

先用自己的话复述一遍下面的计划给提问的人确认，再动手。然后按六组分工，每组派一个 subagent 并行写，主 agent 收齐后统一去重和核对来源。

| 组 | 从哪些样例写什么 |
|---|---|
| 硬件（BMC / iBMC） | 电源、温度、风扇、ECC、光模块的正常值与异常分级 |
| Host / CPU | 主机侧瓶颈的判断依据、绑核与 NUMA 的约束、绑核的副作用与回退 |
| Prof 判读 | 每类分析怎么看、指标含义与单位、快慢卡怎么判、什么情况下不下结论 |
| 日志取证 | 取证步骤、证据怎么记（文件、行号、原文、时间）、先找第一个错误 |
| 环境与版本 | 快照字段含义、组件版本配套关系、缺字段不等于异常 |
| 推理调优 | 量化与投机解码对精度和性能的影响、配置基线 |

每一条（一个文件）必须写清五件事：

1. 结论是什么；
2. 依据哪段原文（引 `answers.md` / `sources.md` 的具体行，或样例里的原始输出）；
3. 适用于哪些平台、哪些版本；
4. **什么情况下不成立**；
5. 来源等级：能逐字对到官方文档的写「官方」，只有手记的写「经验」。

写到 `references/<类别>/<编号>.yaml`，另交一份清单：编号 / 类别 / 补的是哪个诊断空白 / 来源等级。

## 流程约束（做不到，这条分支的实验结果作废）

1. 只加条目，不改诊断步骤、不加工具。想改流程的另开分支。
2. 每条都要写「什么情况下不成立」。写不出来说明还没想清楚，不许入库。
3. 来源分「官方」和「经验」两级，不许把经验写成官方。
4. 每条要能回答「补的是哪个诊断空白」。答不上来就是复述，不算融合。
5. 加之前先和现有条目比一遍，重复的并进去或标成同一主题的另一个平台。
6. 加之后跑一次读量检查（`python3 scripts/index_read_cost.py`）；超线就分批加。
7. **跑题时必须真的用上这些条目**：诊断记录里写清引用了哪几条，并说明它改变了什么判断（按原来的依据会怎么判、现在怎么判）。一条都没用上的题，按对照组算，不算这个版本的成绩。

## 怎么比较效果

同一批题，三个版本各跑一遍：现在的 sleuth（对照组）、版本 A（这条分支）、版本 B（另加工具的那条分支）。

每题在跑之前先写死正确答案，防止事后改标准。每题只跑一次；判定为「材料不够、无法判断」的题才允许重跑一次并记原因。

比三个数：根因说对的题数、第一轮就问对关键事实的题数、给出可执行修复方案的题数。

合格线：版本 A 比对照组多答对 10% 以上才算有效；不到就说明这些经验对诊断没帮助，知识库不动。

## 现在什么状态

分支里还没有条目。第一批建议从 Prof 判读和日志取证开始——这两块的官方出处好找，来源能标成「官方」，最有说服力。
