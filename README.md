# 实验分支 B：让诊断流程能直接调用这 8 个分析器

这条分支是实验分支，首页临时换成这份说明，方便对照查看。项目原本的说明在 [main 分支](https://github.com/pillumina/ascend-sleuth)。

一句话：知识库不动，只给诊断流程加一个「调用分析器」的能力，让它能读整包数据（prof 目录、iBMC 收集包、日志包、ftrace 采集包）并给出结论。

## 原作者需要提供什么

1. **样例数据**：每个分析器 2–3 份脱敏后的输入（prof 目录、`dump_info`、日志包都行），附上你这边的运行命令。没有样例我们无法确认「跑起来了」和「跑对了」。
2. **正确答案**：每份样例的根因和正确处置。这一栏只有你知道；实验判定全靠它。
3. **运行环境说明**：需要哪些 Python 包与版本、要不要 `msprof-analyze`、哪些输入已知会让分析器报错或给出不可信的结论。

## agent 怎么做

每一题派一个 **subagent** 独立跑完整诊断，互不通气；主 agent 只负责发题、收结果、核对有没有真的用到分析器。

- subagent 拿到题目和数据路径，按 sleuth 的 `/diagnose` 流程走；
- 判断手上有整包数据时，调用 `sleuth_analyze(分析器名, 数据路径, 这次要回答的问题)`；
- 拿到返回后读结果文件，把用到的发现写进结论；
- 工具不在、报错、超时，就走原路子，并写明原因。

## 必须产出

- 每题一份诊断记录和一份定位报告（位置和字段沿用 sleuth 现有约定）；
- 调用过分析器的题，多一份结果文件（`traces/evidence/<会话>/tool-runs/` 下）；
- 一张汇总表：题号 / 调了哪个分析器 / 结论有没有用上它的发现 / 没用上的原因。

## 流程约束（做不到，这条分支的实验结果作废）

1. **手上有整包数据就必须先试分析器**。不许绕过它直接凭经验猜；工具不可用才允许走原路子，且要写明是哪一步不可用。
2. **调了就必须读结果**。结论里要能指到具体哪条发现；只贴一个文件路径不算用过。
3. **分析器的发现只当证据或候选解释**，不能直接当根因。根因、修复方案、风险等级仍由诊断流程给。
4. **失败要如实写**：缺依赖、超时、格式不支持，都记下来；不许写成「没有发现问题」。
5. **不替你装软件、不改机器设置**。这些只写进建议，由你决定做不做。

## 怎么比较效果

同一批题，三个版本各跑一遍：现在的 sleuth（对照组）、版本 A（另加知识条目的那条分支）、版本 B（这条分支）。

每题在跑之前先写死正确答案，防止事后改标准。每题只跑一次；判定为「材料不够、无法判断」的题才允许重跑一次并记原因。

比三个数：

- 根因说对的题数（说对 / 说对一半 / 说错）；
- 第一轮就问对关键事实的题数（关键事实在答案里预先列出）；
- 给出可执行的修复方案的题数。

合格线：版本 B 要明显好过版本 A 才值得做这层工具；不比 A 好、又更慢更贵，就只保留 A。

## 现在什么状态

调用能力（接线）做好了，8 个分析器本身还没打进来，现在调用一律返回「未安装」。所以**这条分支现在跑出来等于对照组**。

先验收接线：装上插件 → 工具出现 → 调一次看返回 → 关掉一行看工具消失。等第一个分析器（建议日志取证那个，纯标准库、好跑）打进来，再开始正式比。
