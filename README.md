# 实验分支 B：让诊断流程能直接调用这 8 个分析器

这条分支是实验分支，首页临时换成这份说明。项目原本的说明在 [main 分支](https://github.com/pillumina/ascend-sleuth)。

一句话：知识库不动，只给诊断流程加一个「调用分析器」的能力，让它能读整包数据（prof 目录、iBMC 收集包、日志包、ftrace 采集包）并给出结论。

## 你（原作者）只要做一件事

把三样东西放进一个目录，然后把目录路径贴给 agent：

```
analyzers-input/
├── samples/        每个分析器一个子目录，放 2–3 份脱敏后的输入
│                   （prof 目录、dump_info、日志包都行，目录名用分析器名字）
├── answers.md      每份样例的正确答案：根因是什么、正确处置是什么
└── sources.md      这份样例是用什么命令跑出来的、要装哪些包、哪些输入会让分析器报错；
                    已知会给出不可信结论的情况也写在这里
```

然后只要说一句：

```
材料在 D:\analyzers-input
```

剩下的 agent 读完这份文件自己去做。

**为什么只要这三样**：没有样例，「跑起来了」和「跑对了」分不开；没有答案，判定没有依据；没有运行说明，agent 不知道要装什么、哪些结果不能信。

## agent 读到这里要做什么

先用自己的话复述一遍下面的计划给提问的人确认，再动手。

**第一步，跑通样例**（先做这个，别急着跑题）。对 `samples/` 下每份输入调一次：

```
sleuth_analyze(分析器名, 数据路径, 这次要回答的问题)
```

把结果和 `answers.md` 对照，记三种情况：跑通且结论对、跑通但结论不对、跑不通（缺依赖 / 超时 / 格式不支持）。跑不通的先按 `sources.md` 补环境，补不上就照实记，不要跳过。

**第二步，跑题集**。每一题派一个 subagent 独立跑完整诊断，互不通气；主 agent 只负责发题、收结果、核对有没有真的用到分析器。

- subagent 拿到题目和数据路径，按 sleuth 的 `/diagnose` 流程走；
- 判断手上有整包数据时，先调分析器；
- 拿到返回后读结果文件，把用到的发现写进结论；
- 工具不在、报错、超时，就走原路子，并写明是哪一步不可用。

## 必须产出

- 每题一份诊断记录和一份定位报告（位置和字段沿用 sleuth 现有约定）；
- 调用过分析器的题，多一份结果文件（`traces/evidence/<会话>/tool-runs/` 下）；
- 一张汇总表：题号 / 调了哪个分析器 / 结论有没有用上它的发现 / 没用上的原因。

## 流程约束（做不到，这条分支的实验结果作废）

1. **手上有整包数据就必须先试分析器**。不许绕过它凭经验猜；工具不可用才允许走原路子，且要写明是哪一步不可用。
2. **调了就必须读结果**。结论里要能指到具体哪条发现；只贴一个文件路径不算用过。
3. **分析器的发现只当证据或候选解释**，不能直接当根因。根因、修复方案、风险等级仍由诊断流程给。
4. **失败要如实写**：缺依赖、超时、格式不支持，都记下来；不许写成「没有发现问题」。
5. **不替你装软件、不改机器设置**。这些只写进建议，由你决定做不做。

## 怎么比较效果

同一批题，三个版本各跑一遍：现在的 sleuth（对照组）、版本 A（另加知识条目的那条分支）、版本 B（这条分支）。

每题在跑之前先写死正确答案，防止事后改标准。每题只跑一次；判定为「材料不够、无法判断」的题才允许重跑一次并记原因。

比三个数：根因说对的题数、第一轮就问对关键事实的题数、给出可执行修复方案的题数。

合格线：版本 B 要明显好过版本 A 才值得做这层工具；不比 A 好、又更慢更贵，就只保留 A。
