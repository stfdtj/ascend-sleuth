# 工作机诊断对照实验计划

持有测试集和验证集的实验组织者在自己的工作机上运行本实验。收到本页的主 agent 负责盘点数据、组织盲测和汇总结果。实验要回答两个问题：Sleuth 接入后能否从原始材料提取正确证据？在诊断质量达到同一要求时，开放分析器能否减少模型的工具调用、补证、耗时和读入文本量？

## 第一步：组织者提供路径，主 agent 盘点并选题

组织者只需给主 agent 能读取的数据路径。两套数据放在一起时给一个根目录即可；答案单独存放时附上答案路径。

主 agent 自行识别目录、压缩包、清单或表格，检查索引和样本结构，再建本地案例清单，每行记匿名编号、原始输入位置、所属集合、适用分析器、答案来源、开发或调试时是否用过、首轮可见材料、可按需补充的材料。保持原件，用独立副本运行。

按实际用途选题。测试集中开发时用过的样本适合检查工具接入。正式诊断对照优先用有独立答案、开发时未用过的验证案例。两个集合若有同一事件的副本或派生包，只计一个案例。主 agent 将集合用途或答案来源存疑的案例标为待核，先运行材料可核实的题。开发使用历史或答案依据无法从随附资料确认时，再向原作者核实。只有预期工具输出的案例用于工具核对，缺独立答案的题记录为无法盲评。

下列七项独立实验各优先选两个独立事件，各出一题。材料不足时记下缺口和实际题数。人为移除字段的题标为模拟缺项。主 agent 依据已有答案和原件，在开跑前固定每题可接受的结论、必需证据位置与原值、未知范围、最少补证和误判条件。答案只交给评审。

## 第二步：用测试集验收接入

六项 CLI 进行工具接入验收。固定上游版本和 Sleuth 运行版本。所有正式组使用独立克隆，检出 `da23174e6ec1f4488ffe1d68131a774076e0b882`。准备 Python 3、PyYAML，在该提交运行 `python -m unittest tests.test_analyzers`。启用 `SLEUTH_ANALYZERS=on` 后运行 `python scripts/analyzers/cli.py status --json` 核对安装状态。

对这六项 CLI，主 agent 在本机用同一测试输入分别跑原工具和 Sleuth 适配器，只比较双方保留的功能。每次记录输入、命令、版本、状态、关键读数、单位、缺项和原始证据位置。差异按原件及预期答案裁定。先排练一次会话记录导出，确认工具请求、返回正文和真实起止时间可回查。需要修实现时记录失败样本，新版本另起一轮对照。

prof-compare 单独验收判读词条。组织者从工作簿或原始明细核对基准端、对比端、读数和单位，并在派发前验证只有 B 能读取指定词条。该项直接进入 A/B 诊断对照。

## 第三步：主 agent 分批派发验证集

每个实验单独成批，按材料就绪情况排期。六项 CLI 实验每项两题，各派 A、B、C 三组，共 36 次诊断。prof-compare 单独比较 A、B，两题共 4 次。七项备齐时共 14 题、40 次诊断。同机每次只运行一个正式计时会话，跨题轮换 ABC、BCA、CAB 顺序。并发名额有限时顺次派发，同一 subagent 只做一题一组。

| 组 | 发给子代理的材料与能力 |
|---|---|
| A | 题干、初始材料和共用参考资料，可搜索、读文件、跑通用 Python。分析器开关 off。 |
| B | A 的能力，加一条提前固定的当题判读提示。分析器开关 off。 |
| C | 与 B 逐字相同的提示和材料，额外提供 CLI 调用语法与执行权限，开关 on，由模型自行选择是否调用。 |

主 agent 按组保存允许读取的资料清单，向各组工作目录只提供清单中的参考资料，限制检索范围。派发前从 A 的检索范围搜索 B 专属提示及 prof-compare 词条，确认均不可读，再从 B 检查能读到当题提示。分派手册中有关结果判读和输入缺项的说明如需提供，逐字发给 B、C。C 的额外说明仅含命令、参数和输出路径。

组织者提前为每类题写一条不含答案和工具命令的提示，例如双集群题用“先核对负载、rank 映射和共同 Step，再计算阶段差值”。三组固定模型、推理设置、输出限制和预算。每次使用独立克隆、会话、输入副本和输出目录。关闭自动同步，启动 trace 时传 `--no-sync`，分析器显式指定 `--out-dir`。多卡采集使用可写副本。

给每个子代理单独派发下面的指令，填入对应组的权限和路径。子代理从空白上下文启动，组织者保管本页及案例清单。

> 在指定工作目录按 diagnose 从头诊断这份材料。给出结论或目前能确定的范围，列出原始证据位置、值和单位，说明下一步及最少补证。只使用派发的材料和权限。跳过已有案例、历史复盘、旧 trace、测试集答案、实验说明和其他会话结果。A、B 跳过分析器手册、适配器和 vendor 目录。在首次请求补证时一并提交首轮判断、原始证据、未知项和所需材料。将最终报告与本次 trace 写到独立输出目录。

主 agent 先保存首轮记录及其时间，再按预定内容答复。后续每轮登记新增材料与收到时间。全程未补证时，同一份报告兼作首轮和最终记录。保留 C 未调用、选错、失败、部分成功及回查原文的记录。发生串组或答案泄露时记录原因，为同题所有参评组重新派发干净会话。

## 第四步：盲评诊断质量，再算效率

评审先只看匿名首轮记录和首轮可见材料，锁定评分后再看最终报告及该组实际收到的补证。首轮和最终评分分别列出，效率配对使用最终诊断的验收结果。收齐同题各组报告后隐藏组名、工具身份及效率数据，保留可核对的证据编号。两名评审独立按原五项评分：结论、原始证据、观察项处理、缺证据处理、补证。每项 0–2 分，总分 10。0 分为错误或漏答，1 分为方向合理但证据或动作不清，2 分为判断与证据吻合或动作具体适用。证据不足时准确说明未知和所需补证也可得满分。保留两份逐项评分及分歧依据。

### 正确性指标

主 agent 在盲测前按独立答案列出每题必报事实、可接受的结论、必须保留为未知的事项和数值允许误差。评审逐项回原件核实。工具输出和模型报告各算一份，方便定位错误发生在哪一步。工具之间读数一致时仍需对照原件。以下指标另报原始计数，不折进原 10 分。

| 指标 | 计数方式 |
|---|---|
| 必报事实召回率 | 正确报告的必报事实数 / 答案中必报事实总数。要求数值落在事前约定的误差内，并核对单位、对象和时间窗。 |
| 事实准确率 | 原件支持的事实声明数 / 输出中可核验的事实声明总数。同一事实重复出现只计一次。另列错值、错单位、错对象和原件不支持的声明。 |
| 证据引用正确率 | 能按所引位置找到原值且支撑对应声明的引用数 / 全部引用数。必报事实缺引用时另记漏引数。 |
| 结论命中率 | 最终判断落在预先约定的可接受范围内的题数 / 有独立判定依据的题数。缺项题以首轮实际可见材料为准，允许正确判断为未知或不可比；收到补证后按当时可见材料评定。 |
| 缺证据误判数 | 逐题记录把缺项当零、把不可比数据直接归因、把观察项升为已证实故障的次数，附原句及原件位置。另报发生此类误判的边界题数 / 可评边界题数。 |

分母为零记“不适用”，缺独立依据记“无法核验”。工具只承担提取时，结论命中率用于诊断报告。分项结果按实验、组别和材料是否充足列出。

同题先比 B → C，回答增加分析器的效果。另比 A → B，回答提示的效果。两组均达到该题预先固定的验收条件后，再给四项效率分。每项独立报原值、差值和 0–2 分。达到下表改善幅度给 2 分，反向达到同一幅度给 0 分，其余给 1 分。

| 指标 | 计数口径 | 改善幅度 |
|---|---|---|
| 取证工具调用 | 按模型发起的实际请求计读、搜、Python、分析器查询和执行、回读、失败及重试。并行请求分别计，一次 shell 请求计一次。另列诊断窗口内全部工具调用数和已知子进程数。 | 至少少 1 次 |
| 补证轮数 | 一条补证消息计一轮，另记该轮索取的材料及能否提供。 | 至少少 1 轮 |
| 有效诊断耗时 | 从收到题干到提交最终报告的墙钟时间，扣除仅等待人工答复的时间。计入工具运行和重试。 | 至少缩短 30 秒和基准耗时 10% 中的较大者 |
| 工具返回文本量 | 累加模型实际收到的工具响应正文 UTF-8 字节，包括截断后的正文、错误及重复读取。 | 至少减少 1 字节和基准字节数 10% 中的较大者 |

## 交付物

每批在工作机保存案例清单与版本、各 CLI 的上游和适配器对照表、各组资料清单、匿名首轮记录、补证时间与内容、最终诊断报告、会话工具记录、诊断 trace、工具产物、两份盲评分和逐题配对表。汇总表每行写题号、比较组、两组质量分、四项原值和差值、工具状态及证据位置。缺记录填“无法比较”，质量未达标的配对保留原始读数和原因。

组织者的批次小结写清哪些输入有收益、哪些增加回查或误判、哪些材料仍缺。最终按指标报告改善、持平、变差和无法比较的题数及有效分母。原始材料和答案留在获准工作目录，对外分享脱敏汇总。

以下七项各自选题、派发子代理、评分并交付一份结果表。跨项汇总时保留各项的样本数和证据，不同分析器的得分分开列出。

## iBMC 硬件告警实验

- **材料与操作**：充分题用能核对告警、设备位置和读数的一键收集包。缺项题选有电源事件但缺 NPU 在位记录的包。用测试集对照原解析器与 `ibmc_analyzer`，重点回查电源类型、ECC 计数和原事件位置。
- **交付与验收**：提交逐设备的告警、原始读数与缺项表。验收时核对在位未知是否被误判为丢卡、电源阈值是否适用当前设备。三组均按上述质量和效率标准比较。

## issue-analyzer 多机中断日志实验

- **材料与操作**：充分题提供失败 rank 的框架栈、设备与 Host 日志，时间窗可对齐。缺项题只给设备侧日志或移除跨机时间对应关系。比较工具提取的首条有效事件与原文。
- **交付与验收**：提交含主机、rank、时间和原始位置的事件表。评审核对重复报错的归并依据，以及缺少时间对应关系时能否限定跨机先后判断。

## ascend-dump-analyzer 环境快照实验

- **材料与操作**：两题各准备至少两份快照 JSON。充分题含已知变更及复测记录，缺项题至少一端缺关键版本。用原作者的 `compare_dumps.py` 和适配器核对字段差异。
- **交付与验收**：提交两端原值、差异方向、缺字段和复测依据。验收时分别核对配置漂移与故障归因；只有版本差异时，报告应保留因果判断。

## prof-compare 性能基准判读实验

- **材料与操作**：充分题提供同负载、同采集范围的基准和对比读数，保留单位与绝对耗时。边界题缺关键指标或使用不同采集窗口。可用现成工作簿，也可用可回查的明细表。主 agent 先用有答案的测试样本核对词条读法。
- **派发与验收**：当前分支仅保留判读词条。每题派两个新子代理，A 使用共同资料，B 另读 `references/methodologies/performance-baseline-comparison-reading.yaml`。提交可比条件、两端原值、绝对差和相对差。评审重点核对 A/B 方向、单位、零基准处理和归因边界。按共用标准报告 A → B 的质量与效率差值。

## cluster-analysis 单次集群采集实验

- **材料与操作**：充分题提供一次多卡采集、预期 rank 和 Step 范围。边界题只覆盖部分 rank 或目标 Step。为各组复制输入目录，通过同一 Step 的计算、通信和等待数据核对慢 rank。
- **交付与验收**：提交实际覆盖与预期覆盖、疑似慢 rank、同窗口证据和竞争解释。只覆盖部分 rank 时，报告须写明可以判断的范围。

## cluster-compare 双集群对比实验

- **材料与操作**：充分题提供两份已有集群结果、基准方向、共同 Step 和 rank 映射。边界题缺共同 Step 或映射。各组先检查可比条件，再核对阶段耗时差值。
- **交付与验收**：提交两端负载、采集窗、对齐依据和差值表。评审回查数值、单位和方向。无法对齐的项目写明缺什么材料才能比较。

## cpu-host-performance 主机调度实验

- **材料与操作**：充分题提供带线程身份的 Host trace 和同期 NPU 对照。边界题仅给 Host 侧读数。对照工具产物与原 trace 中的线程、时间窗和调度延迟。
- **交付与验收**：提交线程级观察、同期 NPU 证据和待验证项。评审分开判断 Host 现象与 NPU 影响。绑核建议仅供审阅。

### 做完得到什么

得到两道题各三份诊断报告，以及一份人工评分表。逐题比较证据准确性、处置建议和补证质量。本轮结果用于判断这两类 iBMC 案例中的收益。

### 准备材料

用未参与迁移开发或测试的两个已定位案例。每题保留首轮可见的原始材料和文件结构，供三组读取相同的只读副本。

| 要找的案例 | 首轮材料 |
|---|---|
| 已确认 NPU 多 bit ECC 异常 | 一键收集包或完整 `dump_info/`。优先找含 `AppDump/CpuMem/npu_info`、`AppDump/CpuMem/npu_ecc_info.json` 的包，保留能核对卡号和计数的原始文件。 |
| 已确认电源输入异常，同时缺 NPU 在位证据 | 一键收集包或完整 `dump_info/`，保留 `AppDump/sensor_alarm/current_event.txt`、`AppDump/BMC/psu_info.txt`。优先选原包就缺 `AppDump/CpuMem/npu_info` 的案例。若用完整包模拟缺文件，先在副本中移除该文件，再为三组复制同一份输入。评审标记为模拟缺项。 |

每题另备一份简短题干，写现场现象、发生时间和当时已知的环境。另存评审答案，写已核实的根因、关键证据所在文件和原值、当时采取的处置及结果，以及首轮不能确定的事项。若允许追问，提前写好可补充的事实。

新增词条已有电源输入丢失、缺 `npu_info` 的示例。第二题选独立的现场事件，用不同的告警或读数检验能否把规则用到新材料上。

案例目录和题干文件用中性编号，包内文件名保持原样。评审答案、工单结论和事后分析放在实验检出之外，评审时再打开。日志与报告留在工作机的获准目录，使用该环境获准处理日志的模型。

### 步骤

1. **检出实验分支。** 工作机需要 Git、Python 3、PyYAML 和可用子代理的 Codex。在工作机的实验目录运行以下命令。已有本分支的克隆时，在该目录执行 `git pull --ff-only`，再检查 Python 依赖并记录本轮提交。

   ```powershell
   git clone --single-branch --branch kb/analyzer-model-trial https://github.com/stfdtj/ascend-sleuth.git analyzer-model-trial
   Set-Location analyzer-model-trial
   python -c "import yaml"
   $trialCommit = git rev-parse HEAD
   $trialCommit
   ```

   把打印的提交固定为 C 组版本。原版诊断固定在 `75f6e39ff8e24afb1b9560a1e66f1b816d493b48`。[分析器目录和用法](scripts/analyzers/README.md)

2. **建 6 个独立本地克隆。** 每个案例和版本组合各用一个克隆。在各克隆检出表中指定的提交，把诊断记录、报告和工具产物写到该次运行的独立目录。此仓库同一克隆内的多个 worktree 默认共享 `traces/`，因此这里用独立克隆。

   | 版本 | 检出 | 提供给子代理的能力 |
   |---|---|---|
   | A | `75f6e39` | 原版 `diagnose`。 |

### 怎么确认做对了

开跑前核对同一题三组的输入副本一致，记录各工作目录的 `git rev-parse HEAD`。从每个克隆运行 `python scripts/shared_dir.py traces`，确认 6 个输出路径各自独立。在 C 的运行环境执行 `python scripts/analyzers/cli.py status --json`，确认 `enabled` 为 `true`，`ibmc_analyzer` 的 `installed` 为 `true`。C 若调用失败或没有调用也保留结果和原因。

六份报告收齐后，隐藏版本标签，交两位评审独立打分。分别评根因、证据、观察项处理、缺证据处理、补证。每项 0–2 分，满分 10 分。记录分歧及其依据，另记工具执行状态。

每项按同一尺度打分。0 分表示错误或漏答，1 分表示方向合理但说不清证据或动作，2 分表示判断与证据一致，或行动具体且适合现有证据。首轮确实缺证据时，说明未知并准确提出补证，也可得满分。

### 出错了怎么办

- 检出 `75f6e39` 时报提交不存在，检查克隆是否用了 `--depth`。浅克隆可从实验分支执行 `git fetch --unshallow` 补齐历史。
- 找不到合适的真实材料时，可用仓库样例试跑流程，将结果标为开发验收。后续用两份新案例做效果对照。
- 任一子代理读到了历史案例、答案或其他组结果时，保留该次记录，用干净目录重跑该次。并发不足时，按案例分两批。

### 怎么结束和清理

把报告、评分表和版本记录移到工作机上指定的留存目录，再移除临时克隆。原始材料和评审答案保留在各自的目录。
